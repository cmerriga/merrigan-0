Should be the one-stop-shopping to use any proven, solid common functionality provided by Merrigan.

Layers of this project:
- Basic testing utilities: Testing
    - To support test executor, continuous text executor
- Standard .NET utilities: DotNet
- Standard logical utilities: Merrigan root
- 100% event-based data structures: EventBased
- Contexts with frames: Contexts
- Programmatic text interface for contexts: ContextCommands
- Windows console for contexts: ContextConsole
- Layer that reifies execution and provides full reversability: TrackedExecution
- Automatic testing utilities: AutomaticTesting
- Prospective execution, memoized caching: Memoized
- Data access via (graph query, full language) to (SQL, files, contexts, other data mounds): DataMound
- Data mound chains via in-memory, pipe, TCP: Interprocess
- Actor/pipeline execution with single-thread + thread-dedicated operations like disk: Pipelines
- Marketplace for operation execution over TCP: Marketplace
- CDD utilities (situations, probabilities, learning, promotion, permissions, full language, native interface): Cdd
- Windows console for CDD
- CDD-powered graphics: Windows
- CDD-powered graphics: HTML/CSS
- Hybrid console for CDD

Items from earlier layers may not access items from later layers
Items from later layers may access items from any previous layer back to the last = sign

Conventions
------------------------------------------------------------------------------
function signatures
    reference objects must not be null unless labeled by [MayBeNull]
    reasonable hints may be given if it is a likely scenario that some hard-won data is already known
        example: type = null, but can be provided if a type was already determined
names
    Value is for specified Ts or things that work like generics, like different types of Gloms
    o/appropriate is for objects
    Item is for group member

What would I want to do with drawing?
1. Set {quantized area: pixel XY, rect XYWH; area: circle XYR, ellipse XYRR, triangle XYXYXY, rect XYWH, line XYXYW} to color C on {pixel grid: window W, image I}
2. Set image I on {pixel grid: window W, image I}
3. Set text in color C on {pixel grid}
4. Draw gradient with quick halftone
5. Apply RGB array to screen
6. Overlay RGBA array over screen
7. Define all of the above as permanent, probably via saved operations chain

Behind the scenes, though, what do other things need?
1. Be able to suck out any rectangle of pixels at any time. (Windows will use this)
    a. Might need some proactive, and some reactive.
    b. Need tasks shelf--prioritized based on urgency that adds to 1.
2. Be able to suck out a region. Strategy, divide wisely into rectangles. (Image coalescing may use this)
3. Be able to reach into the structure and convert to similar structures. (HTML might use this)

- Everything that is a one-to-one relation to wrapped/adapted objects should be possible from any one of the instances.
    Example: given a WindowsImage, you can always get its Image
        given an Image, if it is also a WindowsImage, you can get that via "TryAs()"
GridXxxx objects are shapes that are aligned to integer boundaries
